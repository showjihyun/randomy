# J010 검색 API

계획 P001 작업 C. 저장한 노트(제목·원문·요약)와 결정 사항을 검색어로 찾는 `GET /api/search`를 만든다. 검색 로직은 D(질문 답변)가 다시 쓰도록 라우터와 분리된 순수 함수로 둔다. 모델은 부르지 않는다.

## 설계 (사람이 합의함)

- 새 모듈 `backend/src/randomy/search.py`:
  - `search(db_path, query, limit=20) -> SearchResult` 순수 함수. `SearchResult`는 `notes`·`decisions` 두 목록을 가진다. 노트 항목은 `id`, `title`, `snippet`, `created_at`, 결정 항목은 `id`, `note_id`, `note_title`, `text`, `created_at` 속성을 가진다 (응답 JSON과 같은 이름).
  - `create_search_router(db_path)`를 `main.create_app`에서 `include_router`한다.
- notes는 `notes LEFT JOIN summaries`로 title/body/summary를, decisions는 `decisions JOIN notes`로 `note_title`을 얻는다.
- 검색어를 공백으로 나눈 단어마다 `LIKE ? ESCAPE '\'` 조건을 만들어 AND로 묶는다. 단어 안의 `\`, `%`, `_`는 이스케이프해 글자 그대로 찾는다.
- 기존 표(notes, todos, summaries, decisions) 구조는 바꾸지 않는다. 새 표·인덱스를 만들지 않는다.

## 요구사항

### `GET /api/search?q=<검색어>`

- 200, `{"notes": [{"id", "title", "snippet", "created_at"}...], "decisions": [{"id", "note_id", "note_title", "text", "created_at"}...]}`.
- 노트: 검색어의 모든 단어가 각각 제목·원문·요약 중 어딘가에 들어 있으면 맞는다 (단어마다 다른 필드여도 된다). 요약이 없는 노트(`POST /api/notes`)는 제목·원문만 본다.
- 결정 사항: 모든 단어가 결정 사항 `text`에 들어 있으면 맞는다. `note_title`은 그 결정이 속한 노트의 제목.
- 대소문자를 가리지 않는다 (SQLite `LIKE`의 기본 동작, ASCII).
- 정렬: 최신순 (`created_at` 내림차순, 같으면 `id` 내림차순). 각 목록은 최대 20개.
- `snippet`: 원문(body)에서 검색어 단어 중 가장 먼저 나오는 위치 주변의 일부 (원문의 연속된 부분 문자열, 최대 120자, 일치한 단어를 포함). 원문이 짧으면(120자 이하) 원문 전체. 원문에 일치가 없으면(제목·요약에서만 맞음) 원문 앞부분.
- 일치가 없으면 `{"notes": [], "decisions": []}`.
- `q`가 없거나, 비었거나, 공백뿐이면 422.

## 제약

- 기존 API(`/api/notes`, `/api/todos`, `/api/organized`, `/api/decisions`) 동작과 표 구조는 바꾸지 않는다.
- `settings.py`, `model.py`, `evals/`, `skills/`, 화면(frontend)은 바꾸지 않는다. 새 의존성 없음.
- 테스트는 모델을 부르지 않는다.
