# J008 정리 결과 저장 API

계획 P001 작업 A. 확인·수정을 마친 정리 결과(노트 원문 + 요약 + 결정 사항 + 할 일)를 한 번의 요청으로 원자적으로 저장한다. 결정 사항은 이후 검색(C)·주간 정리(F)가 읽을 수 있도록 별도 표에 둔다. 모델은 부르지 않는다.

## 설계 (사람이 합의함)

- 새 모듈 `backend/src/randomy/organized.py`에 `create_organized_router(db_path)`를 두고 `main.create_app`에서 `include_router`한다.
- 표 (모두 `CREATE TABLE IF NOT EXISTS`):
  - `summaries(note_id INTEGER PRIMARY KEY, summary TEXT NOT NULL)`
  - `decisions(id INTEGER PRIMARY KEY AUTOINCREMENT, note_id INTEGER NOT NULL, text TEXT NOT NULL, created_at TEXT NOT NULL)`
- `notes`·`todos` 표에 쓰는 SQL은 `notes.py`·`todos.py`와 같은 형식을 따른다 (`created_at`은 `datetime.now(UTC).isoformat()`, 할 일 `done`은 0).
- 한 sqlite 연결의 `with conn:` 블록 안에서 notes → summaries → decisions → todos 순으로 INSERT한다.

## 요구사항

### `POST /api/organized`

- 본문: `{"title": 문자열, "body": 빈 문자열이 아닌 문자열, "summary": 문자열, "decisions": [문자열...], "todos": [{"task": 빈 문자열이 아닌 문자열, "owner": 문자열|null, "due": 문자열|null}...]}`
- 성공: 201, `{"note": NoteOut, "summary": 문자열, "decisions": [DecisionOut...], "todos": [TodoOut...]}`
  - `NoteOut`은 `POST /api/notes`의 응답과 같은 형식 (`id`, `title`, `body`, `created_at`).
  - `DecisionOut` = `{"id", "note_id", "text", "created_at"}`. `note_id`는 새 노트의 id. 요청 순서대로 돌려준다.
  - `TodoOut`은 `GET /api/todos`와 같은 형식, `note_id`는 새 노트 id, `done`은 `false`. 요청 순서대로 돌려준다.
  - `decisions`·`todos`가 빈 배열이어도 저장된다.
- 검사 실패(`body`가 비었거나 없음, `todos` 중 `task`가 비었거나 없음, 필드 형식이 틀림): 422, notes·todos·decisions 어디에도 아무것도 늘지 않는다.

### `GET /api/decisions`

- 모든 결정 사항 `DecisionOut[]`, 최신순 (`created_at` 내림차순, 같으면 `id` 내림차순).

### `GET /api/notes/{note_id}/organized`

- `{"summary": 문자열|null, "decisions": [DecisionOut...]}`. `decisions`는 그 노트의 결정 사항을 저장한 순서(id 오름차순)로.
- 요약이 없는 노트(예: `POST /api/notes`로 만든 노트)는 `{"summary": null, "decisions": []}`.
- 노트가 없으면 404.

## 제약

- 기존 `POST /api/notes`, `/api/notes/{id}/todos` 동작과 notes·todos 표 구조는 바꾸지 않는다.
- `settings.py`, `model.py`, `evals/`, 화면(frontend)은 바꾸지 않는다. 새 의존성 없음.
- 테스트는 모델을 부르지 않는다.
